## 0. プロジェクト概要

- **用途**: 主に自分用だが、数人の友人にもVercelデプロイ経由で使用させる想定。
- **プラットフォーム**: スマホ利用がメイン。PWAとして疑似スマホアプリ化する。将来的にはWebへの一般公開も視野に入れている。
- **特徴**: **ピクセルゲーム調のUI**で「触っていて楽しい」操作感を作る。デザインの正本は `docs/pixel-style-guide.md`。
  ピクセルアートは blur も滑らかなグラデーションも使わないため、モバイル（iOS Safari）の描画負荷も構造的に軽い。

> **2026-09-04 以前の方針（無効）**: SVGフィルターによる Gooey エフェクト、
> ガラス/グラスモーフィズム、オーロラ背景、巨大 blur などの「リッチなUI」を採っていたが、
> **iPhone での描画負荷とクラッシュ**（`docs/ai-error-log.md`）を受けて破棄した。
> 実装コードは一部残っているが、**新しく作るときの参考にしないこと**。

## 1. アプリの目的（Why）
- Todo機能を核に、日々の行動と気づきを軽く記録し、継続しやすい導線で振り返りに繋げる。

## 2. 主要コンセプト（What）
- **1日の最小単位は Todo**（やること/やったこと）
- Todo に **短い日常メモ**（感情・体調・学び等）を紐づけられる
- その日を「終える」動作で、一覧/ふりかえりに自然に繋がる
- **よくある簡素なTodo UIではなく、「触っていて楽しい」直感的な操作感**
  - 視覚的なフィードバックとモーションを重視する
  - **ピクセルゲーム調のUI**で、日々のタスクを「クエスト」として扱う。
    達成は「カードを下に引っ張って枠に入れる」という物理的な操作で行い、
    RPG風の達成エフェクト（EXP加算・CLEARスタンプ）で報いる
  - 詳細は `docs/pixel-style-guide.md`（デザインの正本）

> **2026-09-05 に方針変更**: 以前は「画面遷移でどこからどこへ移動したかを
> 物理的に視認できるようにする」ため、4画面を2次元空間に配置してカメラを
> パンさせる方式（SpaceNavigator）を採っていた。ピクセルゲーム調への刷新に伴い
> **この空間モデルは廃止**し、画面遷移は通常の切り替えにした。
> 「触っていて楽しい」は、画面遷移ではなく**カード操作と達成演出**で担保する。

## 3. ユーザー像（Who）
- 日々のやることはあるが、日記は続かない人
- 目的は「完璧な記録」ではなく「継続と気づき」

## 4. 機能要件（MVP）
### 4.1 Todo
- **作成**: テキスト入力でTodo追加
- **完了/未完了**: チェックでトグル
- **編集**: テキストの修正
- **削除**: 取り消し可能にするかは後で判断（まずは削除可）
- **並び替え**: 優先度またはドラッグ（MVPでは「追加順 + 完了は下」に寄せる）
- **カテゴリ**: RPGのステータス名に揃えた5種類（2026-09-05 に6種から変更）
  | カテゴリ | 意味 | 色の意味 |
  |---|---|---|
  | `vitality` | 体を動かす・活力 | 赤（HP） |
  | `intelligence` | 学び・知性 | 青（MP） |
  | `creative` | 創作 | マゼンタ |
  | `recovery` | 休息・回復 | 緑（回復） |
  | `quest` | やるべきこと | 金（クエスト） |

  旧6種（routine / health / physical / knowledge / activity / creative）からの変更。
  色は `docs/pixel-style-guide.md` §5 が正本。**コード側は未反映**（影響範囲は同 §7）。

### 4.2 日常記録（ログ）
- **当日ログ**: その日のメモ（短文）を追記できる
- **Todoとの関係**: Todo単位にメモを付ける／または「当日の自由メモ」を持つ（方針は後述の「未決事項」）

### 4.3 日付/ふりかえり
- **日付切り替え**: 今日/過去日の表示切替
- **一覧**: 日毎のTodo + メモを見返せる

### 4.4 タスクソース（Buffs / Overdue / Next）
- **Buffs**: AIが用意した「QOLが上がる」ちょっとしたタスク一覧を表示
  - **Todayへの追加**: 選んだタスクを当日のTodoとして追加できる
- **Overdue**: 達成できなかったタスクを一覧できる
  - **再投入**: 当日のTodoとして再投入できる
- **Next**: 当日ではないが今後やる必要があるタスクを管理できる
  - **追加**: Nextへタスク追加
  - **Todayへの追加**: Nextのタスクを当日のTodoへ追加できる

### 4.6 日跨ぎの仕分け（DAYBREAK）★2026-09-05 決定

**Overdue に入る条件は期限ではない。**
Today に入れたタスクのうち、**その日に達成されなかったものは全て** Overdue へ行く。

`deadline` は「いつまでに確実に終わらせたいか」という**最終的な期日**であって、
Overdue 行きを決める条件ではない。（この2つは無関係）

#### 発火タイミング
**日を跨いだあと、最初にアプリを開いた時**に1回だけ出る。
Today に入る前の関門なので、下部ナビは出さない。

#### やること
きのう Today に残ったタスクを、ユーザーが二択で振り分ける。

| 選択 | 意味 | タスクの行き先 |
|---|---|---|
| **今日やる** | やらなければならない（重い） | 今日の Today に再投入 |
| **あとで** | 次の日以降やらないであろう（軽い） | Overdue に置いたまま |

振り分けが終わったら「今日をはじめる」で、その日の Today に進む。

**なぜ振り分けさせるか**: 残ったタスクを機械的に全部 Today へ持ち越すと、
消化できない量が積み上がって continuity が壊れる。逆に全部 Overdue に置くと、
本当にやるべきものが埋もれる。**1日1回、自分で選ばせる**ことで両方を避ける。

#### 必要なデータ（未実装）
「きのう Today にあった」を判定する手段が現状のスキーマに無い。
`tasks` には `createdAt` はあるが「どの日の Today に置かれたか」を持っていない。
実装には **§7.1 のスキーマ追加が前提**になる。

### 4.5 アカウント（Login / Profile）
- **Login**: サインアップ/サインイン
- **ログイン後導線**: ログイン直後に「アイコンをかっこよく表示する」短い演出画面を挟み、その後 `today` へ遷移したい
- **Profile**: ユーザーのプロフィール画面 + 各種設定

## 5. 非機能要件（MVP）
- **継続性**: 入力が軽い（クリック数・迷いを減らす）
- **パフォーマンス**: 体感が軽い（入力遅延がない）
- **可用性**: ローカル開発で再現できること
- **データ**: Supabase PostgreSQL + Drizzle ORM で永続化

## 7.1 データモデルの不足（実装前に決める必要がある）

現在 DB には **`tasks` テーブル1つしか無い**（`lib/db/schema.ts`）。
`userId` カラムは将来の認証用に空けてあるが、`users` テーブルは存在しない。
以下は「UI が既に表示しているのに供給元が無い」もの。

### (a) 日付 — §4.6 と §4.3 の前提
`tasks` に「どの日の Today に置かれたか」が無いため、
**日跨ぎの仕分けもふりかえりも実装できない。**

追加が要るもの:
- `todayDate: varchar(10)` — Today に置いた日（YYYY-MM-DD）。ローカル日付で入れる
- `completedAt: timestamp` — 達成した瞬間

これがあれば各画面はこう決まる:

| 画面 | 条件 |
|---|---|
| Today | `todayDate = 今日` かつ `done = false` |
| 仕分け対象 | `todayDate < 今日` かつ `done = false` |
| 今日の達成 | `done = true` かつ `completedAt` が今日 |

### (b) 完了タスクの扱い ★2026-09-05 決定
**消さない。`done = true` にして Today から外すだけ。**

- `GET /api/tasks?screen=today` は `done = false` で絞る
  （現在は絞っていないため、達成してリロードすると Today に戻ってくる）
- 完了記録は残るので、ふりかえり（§4.3）と Profile のステータス集計に使える
- ユーザーが明示的に消したいときだけ削除（詳細の「削除する」）

### (c) LV / EXP / コイン — **未決**
Figma の HOME は `LV 7`・`1240 G`・EXPゲージを、達成エフェクトは
`+10 XP`・`+5 G` を表示しているが、**供給元が無い**。2案:

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 集計で出す | 完了タスクの `points` 合計から毎回計算 | テーブル追加が要らない。認証と切り離せる | コインなど「消費する」概念を足せない |
| `users` を持つ | level / exp / coin をカラムで保持 | 消費・報酬を作れる | 認証とセットで設計が要る |

**まず集計で出し、コインを「使う」機能が必要になった時点で `users` を足す**のが
移行コストが低い。ただし §4.1 のカテゴリ5種化と同時にやると影響が広いので順番に注意。
